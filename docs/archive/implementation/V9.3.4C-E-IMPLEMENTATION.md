# V9.3.4C-E Implementation and QA Guide

## Baseline

This package is based on repository commit `3841c8d742803cf97de7d597019674e5746e933c`, after V9.3.4A3 and the current-season refresh. A3 remains the performance baseline. C-E are layered after it through `app/current-snapshot-store.js`.

## V9.3.4C · Lightweight weekly matchup context

`app/v9.3.4c-weekly-context.js` adds `window.FIEWeeklyMatchupContext` / `window.FIE934C`.

For the selected week it performs one cached Sleeper matchup fetch, finds the selected roster and opponent by `matchup_id`, builds projected lineups from the league's actual starter slots, and calculates projected totals. The quick win probability is an analytic normal approximation from the two projected lineup distributions. Player uncertainty uses an existing player interval/CV where available and a position-CV fallback only for the quick uncertainty estimate.

C does not call `runLeagueSimulation()` and does not populate `leagueSim.data.current`. This is intentional. The existing full simulation remains the richer optional path. C follows the live `state.selectedRoster` used by the current decision UI, patches the exact `Modeled win probability`, `Opponent projected total`, and `Your projected total` cells, and also targets the current `#matchupSimPanel`. Existing full-simulation values are never overwritten once they are real values rather than placeholders.

Generation and league guards prevent a stale week/league request from publishing after a switch.

### C acceptance

1. Open Genesis and Start/Sit.
2. Choose a team and Week 1.
3. Opponent projected total and win probability should populate without waiting for full league simulation.
4. Switch Week 1 to Week 2. The app should remain responsive and the context should update.
5. Switch leagues while context is loading. No old-league opponent data may leak into the new league.
6. Full simulation must still work when explicitly requested.

Diagnostics:

```js

FIE934C.report()
```

## V9.3.4D · Universal starter-slot economics

`app/v9.3.4d-starter-economics.js` adds `window.FIEStarterEconomics` / `window.FIE934D`.

The model is universal across Redraft, Dynasty, Chopped, Best Ball and IDP configurations. It has no Chopped special case.

The calculation is:

`league size × concrete starter slots × slot eligibility -> effective positional starter demand -> replacement frontier -> scarcity -> player-level marginal lineup utility`

Direct slots are allocated first. Flexible slots are then allocated against the live marginal player frontier, so Superflex can flow to QB/RB/WR/TE, ordinary FLEX to RB/WR/TE, receiving flex to WR/TE, and IDP flex to DL/LB/DB. FLEX competition is evaluated on a common weekly-points scale: live weekly projection first, season projection divided by 17 second, then public PPG, with normalized decision-score fallback only when projection evidence is absent.

Each player receives:

- `starterEconomics.effectiveStarterDemand`
- `starterEconomics.replacementValue`
- `starterEconomics.replacementAdjustedValue`
- `starterEconomics.starterProbability`
- `starterEconomics.scarcityMultiplier`
- `starterEconomics.floorDownside`
- `starterEconomics.floorAboveReplacement`
- `starterEconomics.marginalLineupUtility`

Convenience mirrors are also attached (`starter_probability`, `replacement_adjusted_value`, `marginal_lineup_utility`, etc.). D then performs one economics-aware rerank after A3 publishes scores, preserving A3 as the base model while adding a bounded league-economics adjustment.

A synthetic 1,000-player / 18-team Superflex test completed the D calculation in roughly 17 ms in local Node testing. Browser timing remains the authoritative performance check.

### D acceptance

1. Run `FIE934D.report()` in Genesis and Chopped.
2. Confirm `effectiveDemand` differs when starter slots/league size differ.
3. In a 1QB league, QB demand should approximate one starter per team plus any actual flex allocation, not an unconditional QB premium.
4. In Superflex, QB demand should rise only as the marginal QB beats eligible alternatives.
5. `starter_probability` should fall sharply around the league-specific replacement frontier.
6. `floor_downside` remains `null` when a real floor/P10 is unavailable.
7. D synchronous timing should stay well below 250 ms, with a target below 50 ms around a 1,000-player pool.

Diagnostics:

```js

```

## V9.3.4E · Return scoring audit and decomposition

`app/v9.3.4e-return-scoring.js` adds `window.FIEReturnScoring` / `window.FIE934E`.

Supported Sleeper player scoring keys:

- `kr_yd`
- `pr_yd`
- `kr_td`, falling back to aggregate `st_td`
- `pr_td`, falling back to aggregate `st_td`

Supported team/DST TD weights are separately audited:

- `def_kr_td`, falling back to `def_st_td`
- `def_pr_td`, falling back to `def_st_td`

No DST return-yard key is invented. Team/DST return-yard scoring remains explicitly unsupported/null unless a verified scoring key and data source are added later.

Verified nflverse player-stat return fields used by E are `special_teams_tds` (documented as total kick/punt return touchdowns), `kickoff_returns`, `kickoff_return_yards`, `punt_returns`, and `punt_return_yards`. TD aliases are used only when such a field is actually present in the row.

### Counterfactual completion

For each public stats row E calculates:

1. legacy fantasy points on the real row,
2. legacy fantasy points after all known return fields are zeroed,
3. the return points the league settings imply.

It then classifies the legacy scorer as:

- `already-complete`, add zero,
- `missing-completed`, add the full missing return component,
- `partial-completed`, add only the missing portion,
- `ambiguous-fail-closed`, add zero rather than risk double counting.

### Projection semantics

Missing return projections remain `null`. E does not infer return yards from historical return volume. If explicit return projection fields become available, E exposes their contribution. It exposes `weeklyProjectionWithReturns` only when source metadata explicitly says the baseline excludes returns; it does not silently mutate an opaque baseline projection.

### E acceptance

1. Let Public Enrichment reach 4/4.
2. Run `FIE934E.report()`.
3. Confirm `scoringKeys` reflect the active league's Sleeper settings.
4. In a return-yard league, players with nflverse return yards should have `returnScoring.actual` and the public-stat completion mode should be visible.
5. `ambiguousLegacyRows` should ideally remain zero.
6. `projectionCoverage` can legitimately be zero when the live projection feed has no explicit return decomposition. This is correct fail-closed behavior, not a missing-data zero.

Diagnostics:

```js

```

Upload the package preserving paths. Then run:

1. `Validate FIE V9.3.4C-E`

3. existing broad V9.3.1 validation
4. allow Cloudflare Pages deployment
5. hard-refresh with `Ctrl + Shift + R`

## Regression guard

The A3 performance targets remain in force. C performs its network work asynchronously, D is a short post-score calculation, and E's return completion runs inside already-background public enrichment. If core interactive time or A3 scoring returns to multi-second territory, treat that as a regression and stop deployment.
