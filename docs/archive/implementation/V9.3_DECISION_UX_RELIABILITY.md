# FIE V9.3 Decision UX & Reliability Consolidation

Release: `9.3-decision-ux-reliability`  
Date: 2026-08-26

## Scope

V9.3 is a product/runtime consolidation around the existing FIE research engine. It does not replace M1-M6 or the league-specific scoring/storage architecture. Its goal is to make the existing intelligence correct, explainable, fast to reach, and decision-specific.

The release implements the product decisions approved for this sprint:

1. Release identity is V9.3 Decision UX & Reliability Consolidation.
2. Draft Board is neutral to the user's currently owned roster, but league starter counts, FLEX/SF eligibility, roster depth, scoring and replacement cutoffs explicitly drive positional scarcity.
3. Dynasty Targets are removed in Redraft and Chopped formats.
4. Useful heuristic signals may be shown only when visibly labelled as estimates rather than calibrated facts.
5. The Weekly win-probability optimizer is opponent-aware without a manual conservative/aggressive slider.
6. The deliverable remains a complete repository plus deployable `dist/`, with deterministic release gates.

## Architectural changes

### Canonical LeagueContext

`app/league-context.js` provides one normalized source of truth for:

- roster slots and counts
- starter slots
- legal positions
- FLEX/SUPER_FLEX eligibility
- QB/RB/WR/TE/K/DST/IDP capability flags
- Dynasty/Redraft/Best Ball/Chopped format flags
- preferred Sleeper owner resolution

The preferred Sleeper username is `C0nstant1n`. It is resolved through Sleeper user ID to `roster.owner_id`; team display names are not used as identity.

This removes independent K/DST/IDP/Superflex interpretation from consumer features and fixes false league-capability states such as Genesis containing `K` and `DEF` while a feature reports that the league does not use them.

### Decision-specific UI

`app/decision-ui.js` and `app/decision-ui.css` replace the legacy "one giant player table everywhere" model for primary consumer surfaces.

The release distinguishes:

- League/Player Value
- Positional Value
- Market Value
- Exact Roster Contribution
- Decision Value

A single generic `FIE Rank` is no longer treated as the correct primary currency for every screen.

### Market comparison

Where possible, FIE-vs-market comparison is positional first, e.g. `FIE WR12 vs Market WR19`, so player evaluation can be distinguished from cross-position scarcity assumptions.

### Confidence semantics

Heuristic/fallback signals are labelled as estimates. Calibrated risk intervals are allowed to use probability labels such as P10/P90; fallback distribution shapes use Low/High or equivalent estimate labels.

## Consumer surface redesigns

### Draft Board

The board remains independent of the user's owned players while being fully league-specific.

Redraft core:

`Draft Rank | Player | FIE Pos | Sleeper ADP | Market Pos | Market Edge | Season Projection | VOR | Tier`

Dynasty core:

`Draft Rank | Player | FIE Pos | Market Rank | Market Pos | Value Gap | Current Value | Future Value | Age`

Best Ball emphasizes ceiling/profile and portfolio construction rather than weekly start/sit concepts.

Chopped emphasizes Weeks 1-4, downside and replacement depth. It does not use the ambiguous label `Survives` for its main board.

### Draft Assistant

The top of the surface now provides three direct choices:

- Best Pick
- Alternative
- Value Play

The candidate table is compact and removes Eligibility. It focuses on market edge, exact roster delta, estimated next-pick availability, action and explanation.

### Value Finder

Value Finder now treats Top 100, ADP 100-200 and ADP 200+ as separate discovery problems. Optional research failures degrade evidence rather than repeatedly destabilizing rendering. Rows use explicit states such as TAKE NOW, TARGET, WAIT, WATCH, FAIR PRICE and INSUFFICIENT EVIDENCE rather than unexplained blanks.

A runtime-contract mismatch was also corrected: roster slot contracts use `.positions`, not the obsolete `.eligible` access pattern.

### Team / Roster Assets

Power & Structure stays visual. Position cards route into Roster Assets filtered to the selected position.

Roster Assets is format-specific and uses exact legal-lineup roster contribution as a central field. Matchup/playoff decision simulation is removed from Team and belongs in Weekly.

### Weekly Start/Sit

The compact weekly table focuses on:

`Slot | Player | Opponent | Week Projection | Low/P10 | High/P90 | Matchup Delta | Bench Delta | Decision | Week Pos Rank`

Season-long VOR and unrelated player metadata are not primary start/sit fields.

Weekly includes:

- maximum expected-points lineup
- opponent-aware maximum modeled win-probability lineup

If both objectives choose the same legal lineup, the interface states that rather than manufacturing a difference.

### Waivers

Rows represent transactions rather than isolated free agents. The primary Redraft representation is Add -> Drop with exact roster delta, weekly delta, next-three delta, FIE positional rank, FAAB and an action.

The player drawer has a context-specific Basic view for action, drop candidate, gains, FAAB and key risk, plus an Advanced analytical view.

### Dynasty Buy Targets

The target surface is available only in Dynasty formats and includes rostered as well as available long-term assets. Redraft and Chopped do not retain a redundant Dynasty Targets tab.

### Trade Center

The legacy control/Ctrl-select interaction is replaced by a two-sided trade builder with asset chips. Evaluation separates:

- Asset Value Delta
- Exact Roster Utility Delta
- Immediate Starter/Lineup Delta
- Future Value Delta in Dynasty
- modeled win/survival effects where available
- final-roster legality

Roster legality is evaluated on the completed post-trade state, not an invalid intermediate state.

### Players Explorer

The explorer is informational rather than transactional. It shows only league-legal positions by default. FAAB strategy and unrelated decision boxes are removed from the primary Players surface.

### D/ST and Kicker Intelligence

Both specialist surfaces use a compact streaming-decision structure. Main tables present rank, opponent/status, projection/risk, replacement delta, short-horizon value and action. Football/model drivers remain available in detail rather than crowding the primary decision table.

### League Intel

League Intel is split into:

1. Manager Behavior, with sample size and confidence.
2. Trade Partner Fit, with needs/surpluses and plausible matching direction.

Historical transaction loading is lazy. Current-season transaction requests are bounded by the current week rather than blindly requesting all rounds 0-18; prior seasons may load the full history.

### Rules & Format

Normalized LeagueContext interpretation is surfaced with compact roster and scoring tables so a user can verify that FIE understood the imported Sleeper league correctly.

## Loading and runtime improvements

### Faster critical path

A league becomes interactive after the core Sleeper league/roster/user/player-map state is available. Public enrichment, projections and research are progressive background enhancements rather than one serialized "fully loaded" gate.

### Data client

`app/core/data-client.js` now supports shared in-memory TTL caching and in-flight request deduplication. Stable player-map data also uses persistent browser caching where available.

### Lazy work

Historical League Intel transactions are not loaded during ordinary league startup. Specialist feature data are allowed to load on demand or from cache.

### Cancellation/staleness

League switches use generation IDs and abort scopes so stale work from the previous league cannot overwrite the new league state.

### Performance instrumentation

Runtime timing captures critical fetches, enrichment, projections, research, request timings and long main-thread tasks. This provides a measurable baseline for further optimization rather than relying only on perceived speed.

### Enrichment failure isolation

Public enrichment runs off the critical path and now has an explicit diagnostic catch path so a global enrichment failure does not become an unhandled background rejection.

## Positional scarcity

V9.3 does not add another arbitrary scarcity bonus. It uses the canonical league demand/replacement architecture.

A deterministic V9.3 scarcity test verifies that an otherwise identical 12-team player pool changes QB demand from 12 in 1QB to 24 in Superflex, and changes the replacement cutoff from QB12 to QB24. This directly protects the approved requirement that Draft Board remain personal-roster-neutral while starter spots drive scarcity.

The Research surface also contains a positional scarcity audit showing legal starter demand, demand/team, replacement cutoff, replacement player and replacement projection.

## Reliability fixes

The sprint found and corrected two important runtime-contract errors where older consumers read roster-slot eligibility from `.eligible` even though the generated contract stores it under `.positions`. The affected areas were Value Finder and Draft Monte Carlo worker context.

The V9.3 UI smoke audit additionally found that three functions referenced by the decision UI initializer were missing definitions. These were implemented before release:

- release synchronization
- positional scarcity audit renderer
- League Intel renderer

This is why V9.3 adds a runtime decision-UI smoke test instead of relying only on JavaScript syntax checks.

## Versioning

`config/release.json` is the canonical release identity. Generated release metadata drives runtime release display, browser title and diagnostics. Production should no longer require manually editing a hardcoded 9.1/9.2 title after each release.

## QA and release gates

The source release gate includes existing architecture/research tests plus V9.3-specific coverage for:

- decision UX source integrity
- league-context runtime behavior
- preferred roster auto-selection
- K/DST/Superflex capability detection
- scarcity behavior
- decision-UI runtime initialization
- Value Finder runtime behavior
- Top-100 optimizer behavior
- deployment artifact hygiene

The deterministic release build regenerates contracts, release metadata and the build manifest, builds `dist/`, then runs the release gate.

## Browser-preview limitation in this build environment

A real visual browser pass was attempted, but the available sandbox blocks local `http://127.0.0.1` and `file://` navigation. Therefore the release is validated through runtime smoke tests, static/source integrity tests, deterministic build checks and the existing release gate, but a final visual check on the deployed Cloudflare preview should still be performed before promoting it to the production URL.

This limitation must not be interpreted as a successful live-browser visual QA pass.
