# M10 real prospective outcomes and paired review

Status: research-only design, 2026-10-08. This is the Sol methodology boundary for the already captured 2026 Week 4 and later weeks. M9 remains the production champion. This design does not authorize shadow traffic, model promotion, runtime changes, or retrospective forecasts.

## Evidence identity and eligibility

Use only an immutable, non-fixture M10 capture whose manifest, paired M9/M10 forecast ledger, profile-scoring ledger, and decision traces validate under the existing capture contract. Outcomes are a *separate*, later first-write revision bound by the SHA-256 of that forecast manifest. Forecasts cannot be reconstructed from a later source. A Week 4 retrospective nflverse player-week archive already exists in `data/operations/weekly-performance/2026/week_04/sources/`; use its envelope and compressed raw response, checking both hashes and the canonical selected-target-row digest. Do not fetch again to replace the archive. For later weeks, wait for the stored schedule's latest kickoff plus the existing PR2 12-hour stabilization buffer, and use the first eligible archived response. The buffer is a freshness rule, not a certification of official game finality.

The outcome adapter must verify a source envelope's season/week/regular-season rows, observation time, archive hash, raw-response hash, target-row count and digest, and scheduled game/team pairing. Join only exact GSIS player IDs from the prospective ledger to exact `player_id` rows. Duplicate player-week IDs, conflicting games/teams, and source rows with missing player IDs must not be guessed into a forecast identity. Missing forecast players stay missing, with explicit typed coverage; an absent provider row is not a zero-point DNP. Store source-native raw components and provider point totals as diagnostics with provenance. A captured row may use source-declared sparse zeros where the archived schema explicitly represents them; blank, unavailable, or unrepresented fields remain unknown. Model-independent outcome rows have exactly one row per frozen forecast ID, including blocked rows with null raw outcomes and an explicit reason. An outcome revision is append-only; a correction needs a distinct later revision with the previous manifest hash and a documented diff.

## Scoring and paired methodology

Exact league scoring requires the *full scoring settings frozen at forecast cutoff*, verified by profile signature and fingerprint against the paired scoring ledger. A current league profile is not a replacement for missing frozen settings. Preflight every nonzero scoring key against source-native fields, their numeric values and scorer aliases (including fumble split versus aggregate semantics and bonuses) before using `fie_research.score_rows`, which otherwise silently fills missing values with zero. Unsupported keys and any ambiguous field block that league/player score. Provider standard/PPR point totals are never an exact league replay. Preserve the frozen scorer version and scoring settings hash in the evaluation lineage.

For each league and position, compare M9, M10_LINEAR, and M10_HGB only on the *identical* observed forecast IDs with the same capture cutoff, matchup, scoring profile, and exact outcome definition. Report the denominator of all eligible captured IDs, observed rows, exactly scored rows, and all exclusion reasons for each group. Compute paired MAE, RMSE, and signed bias from finite point predictions and exact observed scores, with paired deltas against M9 and bootstrap intervals only if enough independent weekly/game units accrue; do not imply independence across league replays of the same player. A single Week 4 can demonstrate ingestion and descriptive paired errors but cannot establish challenger superiority. Quantile calibration may be reported only where the frozen quantiles and scoring semantics agree; do not compare raw-component quantiles to league fantasy-point outcomes. Start/sit, best-ball, and chopped decisions require their own frozen legal-roster and realized-utility evaluation; player-point MAE is not a decision win.

Sunday Sleeper projections belong to the separate `SUNDAY_MAIN_T6` capture and may be compared only on the intersection of pregame, source-aligned identities and a common Sunday cutoff. Never treat the week-open M10 capture and Sunday Sleeper baseline as if they had the same information set. Coverage can be too sparse for comparison, and a typed block is a valid result.

## Implementation boundary

Add a source-bound real-outcome adapter with offline fixture tests for hash tampering, duplicate/absent identity, eligibility, first-write collisions, and source-field nulls. Retain the existing M10 outcome schema and append contract; do not rewrite frozen forecast ledgers. Add an evaluation owner only after frozen full profile settings and score coverage are demonstrably available. The Week 4 source archive is real retrospective evidence, but absent frozen settings or source metrics must remain explicit blockers instead of invented exact league scores. Operational automation may use the stored source after the buffer, never a synthetic fixture. Validate targeted integrity tests and one release gate at closure.

For future captures, persist the producer's exact full profile snapshot as a byte-identical first-write alongside its scoring replay *before* the forecast manifest is finalized, and bind it to the existing input-lineage profile hash. A matching retry is safe, a conflicting retry fails. This leaves Week 4's absent cutoff snapshot explicitly absent; do not backfill it from current league state. The snapshot is research-only and contains scoring settings, signatures and fingerprints needed for later exact-outcome preflight.
